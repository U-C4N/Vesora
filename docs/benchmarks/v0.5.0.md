# Vesora v0.5 linked selection benchmark

This is one observed **SwiftShader software-rendering** run. It is not a hardware-GPU result, FPS measurement, peak-memory measurement, Python bridge benchmark or competitor comparison.

## Reproduce

```powershell
npm run build
$env:VESORA_SOFTWARE_GPU = '1'
npm run benchmark:linked
```

The script writes every latency sample, selection predicate/count, completed sequence, source-byte count, representation and environment field to `artifacts/benchmark-linked.json`. Set `VESORA_CHROME` to select another executable. For a separate hardware experiment, leave `VESORA_SOFTWARE_GPU` unset and check the reported renderer rather than assuming hardware acceleration.

## Environment and workload

- Recorded against the final source-isolation build: 2026-10-11, 18:05:57 UTC / 21:05:57 Europe/Istanbul.
- CPU: Intel Core i9-14900HX; 32 logical CPUs; 31.7 GiB system RAM; Windows x64.
- Browser: headless Chrome 155.0.8059.39, device pixel ratio 1.
- Renderer: `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)`.
- Figure: 1,200 × 520 CSS pixels; 1,400 × 800 browser viewport; two scatter plots and one count histogram in a 1×3 grid.
- Each row has `prediction=(i%1000)/10`, `feature=(i%257)/256`, and `residual=3*sin(i*.173)+2*cos(i*.071)`. Rows with prediction from 60 through 80 and feature at least .8 receive an additional residual of 22. This is deterministic synthetic data, not a measured model result.
- The histogram uses 40 explicit, fixed bins from -6 through 28 in steps of .85. Source rows are aligned by their original ordinal.
- Cases run in order: 100,000 rows, then 1,000,000 rows. Each receives a fresh page in the same browser. No warm-up sample is discarded. Browser-process, shader-cache and background-system state are not fully reset between cases.

The first scatter uses prediction/residual and the second uses feature/residual. Twenty programmatic rectangle selections alternate origin scatter and replace the cohort. Prediction bounds alternate lower x edges 60/62 with upper edge 80 and residual range 15–28. Feature bounds are .8–1 with residual lower edges 15/16/17 and upper edge 28. Repeated predicates are retained as samples.

## Observed results

| Aligned dataset rows | First ready (ms) | Selection p50 (ms) | Selection p95 (ms) | Registered source bytes | Main-page JS heap (MiB) | Membership bitset bytes |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100,000 | 170.3 | 11.6 | 28.3 | 4,000,000 | 16.49 | 12,500 |
| 1,000,000 | 368.6 | 123.3 | 136.1 | 40,000,000 | 48.91 | 125,000 |

Selection cohorts ranged from 3,647 to 4,056 rows in the 100k case and 36,612 to 40,664 in the 1m case. Every request committed its current sequence and a nonempty exact cohort. The 1m case exceeded the 10,000-index preview cap; membership and histogram computation still used the complete cohort. Both cases finished with WebGL error code 0.

The million-row case took about 0.12 seconds at the median under this workload. The result does not establish universal scaling or justify an instant-selection claim for arbitrary million-row data.

## What the metrics mean

**First ready** starts before figure construction and includes source generation, validation, worker preparation, mounting and drawing. It is not a standalone GPU-render time. **Selection-to-ready** starts before the internal viewer selection entry point and ends after `ready()` completes; it excludes initial source generation and pointer movement. Both scatter highlights, the selected histogram and summary must be current before the selection event is accepted. These measurements do not include Python transport or desktop/notebook-host overhead.

Each case has 20 samples. p50 averages samples 10 and 11 after sorting; p95 uses nearest rank, sample 19. No latency sample is omitted. These are interaction latencies, not animation-frame rates.

Registered source bytes count the figure's five numeric source channels; repeated residual channels are registered separately in this example. They exclude caller-owned arrays, worker source copies, cache results, geometry and GPU buffers. Link attachment/import isolates member buffers by copying; caller arrays may coexist with isolated sources until released/collected. Complete membership uses one bit per row (`ceil(N/8)` bytes), retained as derived state in addition to those sources; bounded preview and selected plans add further allocations.

JS heap is Chromium's main-page `usedJSHeapSize` estimate after the final selection, without forced garbage collection. It is not peak or process-total memory and does not reliably account for workers or GPU allocations. Python and GPU memory remain `null` in the raw report. No total-memory or zero-copy claim follows from these values.

Correctness, cancellation, worker/fallback parity, blank/empty selection and offline export are covered by separate tests. A clean timing run does not replace them.
