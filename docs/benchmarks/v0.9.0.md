# v0.9.0 measured evidence

## Tagged RC2 result: performance passed, Jupyter latency failed

The clean tagged `0.9.0-rc.2` build, commit `63f0856858266f115cdfec708c8266a572e4387b`, passed the browser performance gate on 2026-10-15. Manifest SHA-256: `7902c9b94a11c70e78a6a3ae4fc4cc13d4d34a77dcb40067d2cbff56d4e22b6d`; core runtime SHA-256: `632e6d8c38a115827ded63ece2c4e589c9e86483594e8f9384fda25f22a0519f`. Reviewed reports and all raw measurements are retained in `dist/release-v0.9.0-rc.2/evidence/`. These results belong to those fixed archives.

Five paired repeats used the same fixed v0.8 archive, Windows/Chrome 155.0.8059.41, ANGLE SwiftShader, i9-14900HX, 1000 × 600 canvas, DPR 1, seed 42 and unchanged one-million-row workloads. The quiet-run preflight recorded 15% system CPU and 11.77 GB free memory; other applications were left running. Each interaction entry is the median of five within-run p95 values.

| Workload / metric | v0.8 median (ms) | RC2 median (ms) | Change | Gate |
| --- | ---: | ---: | ---: | --- |
| Density first ready | 185.5 | 191.6 | +3.29% | Passed |
| Density interaction p95 | 97.2 | 87.8 | −9.67% | Passed |
| Line first ready | 185.9 | 185.6 | −0.16% | Passed |
| Line interaction p95 | 88.6 | 82.5 | −6.88% | Passed |

The separate 60-second three-series stream completed all 1,199 batches at approximately 19.97 Hz, with p95 **29.1 ms**, p99 **50 ms**, no pending work and zero owned source bytes after close. All 18 scientific 3D matrix runs passed camera geometry/buffer reuse, warm picking-cache reuse and cleanup assertions. This short measurement does not establish the 30-minute optimization targets or two-hour soak gates. The regression, stream and 3D raw report SHA-256 values are respectively `d6f8a10810fe284cc36dac407046b61adafbb94af43bb3491901578a7766a98d`, `3255b64bb67576055abe7bec465a98f9a89696cb64670d303726fcbfa790c63c` and `fa6b721fa5a5d1520a2d75e30a392d0dca803ed27934a265e2cc1c64080716a3`.

Installed-wheel Qt passed all 14 checks with presentation p95 **154.21 ms**. Real JupyterLab passed all 20 functional checks but failed the **300 ms** presentation limit twice: p95 **458.33 ms**, then **518.83 ms** in a separately retained quieter-window recheck. Both original results remain failures. Browser timing cannot substitute for host timing.

A subsequent instrumented run of the unchanged RC2 wheel identified 300 revision-only trait messages, 400 timer creations/cancellations and 330 duplicate frame identities among 472 frame packets in the 100-sample workload. Its p95 was 93.27 ms, but instrumentation and run variability make it diagnostic evidence, not a replacement gate. The traffic counts justify targeted notebook overhead work for RC3; they do not establish the cause of the earlier failures. Worker stage timing was not captured by that probe. No two-hour soak or human pilot result is claimed.

The separate 60.20-second rendered-append workload completed all 1,168 accepted batches with no errors and released its sources on close. Its p95 **296.5 ms** exceeds the required browser **150 ms** limit; p99 was 346 ms. The 18-case 3D matrix passed its camera reuse, picking-cache and cleanup invariants. Those correctness results do not override failed latency gates.

The environment remained Windows/Chrome 155.0.8059.41 with ANGLE SwiftShader, the i9-14900HX CPU, a 1000 × 600 canvas, DPR 1 and seed 42. Absolute times varied substantially between runs, including the baseline. Diagnostic stage runs are exploratory and do not replace the unchanged five-pair acceptance benchmark.

RC2 restored direct typed-array traversal across aligned source chunks and uses a small shader for plain layers, with lazily compiled scientific shaders and cached locations. Dense fully visible streaming lines can reuse exact, bounded min/max indexes for immutable chunks; clipping, gaps and unsupported scales retain the ordinary planner. Query normalization is prepared once, visible line segments avoid unnecessary clipping, and merged chunk bounds reuse entry-owned pairs. Snapshot ownership remains intact. Its measured results are recorded above; absolute timing varies between runs, including the baseline.

## Historical development scientific 3D matrix

The measured build reuses geometry and GPU buffers during camera-only frames. Cached picking is much cheaper than its first index build. These results do **not** establish 60 FPS or interactive 500,000-point performance: the software renderer takes hundreds of milliseconds for the largest orbit frames, and the first 500,000-point pick is a visible pause.

Run the matrix without another browser, Qt, or graphics benchmark running:

```sh
npm run build
node scripts/benchmark-3d-v09.mjs
```

The script writes raw timing samples, diagnostics and provenance to `artifacts/v09/3d-software.json`. The historical run below is preserved separately as `artifacts/v09/history/3d-software-be949776d27e6284.json`. Set `VESORA_SOFTWARE_GPU=0` to measure the browser's default backend separately; its actual renderer is recorded. This measurement used only the software backend.

### Recorded environment and scope

- Recorded: 2026-10-15 08:42:35 UTC; Windows; Intel Core i9-14900HX; 32 logical CPUs; 34,045,042,688 bytes physical memory.
- Chrome 155.0.8059.41, ANGLE Vulkan 1.3.0, SwiftShader Device (Subzero), SwiftShader driver.
- Runtime: `packages/core/dist/index.js`, SHA-256 `b1083ef255ac4f27e93b8e6919b957c4d011b6e43c1d324f7f056e5f38984ca1`. These measurements identify this build, not a different later release artifact.
- Canvas: 1000 × 600, DPR 1. Three repeats per case, alternating case order. One unmeasured small surface and scatter scene precede the matrix; every measured case uses a fresh page.
- Surfaces use the same finite synthetic radial field, smooth shading, no wireframe. Scatter uses seeded uniform spatial coordinates, seed 42, point size 3. No adaptive geometry detail is enabled.
- First-ready time includes figure creation, source registration, mounting and `ready()`, then `gl.finish()`. Data generation is excluded and recorded separately. Each orbit sample includes `ready()` and `gl.finish()`; 30 samples per repeat.
- Cold picking includes the projected index build. Each repeat then records 100 synchronous hover samples at different positions with an unchanged camera. Warm picking includes the committed hover/tooltip path of a bare figure, not a shared viewer sidebar and not only its numeric search.

A camera change invalidates the projected index; the next pick is cold again. An object-space index or asynchronous index construction remains a potential follow-up, not a shipped performance guarantee.

The practical finding is that camera changes reuse GPU data and repeated hover avoids a full scan. The next performance work should address cold-index latency and large-scene draw cost; no speedup against v0.8, hardware-GPU result, automatic LOD, or live-3D throughput is inferred from this matrix.

## Historical development paired v0.8 regression check

Five paired repeats used the archived v0.8 core tarball (SHA-256 `ab36142c084f0b33236e47d248c5ff9ab81bf4b4ef0e0c2bd4f7216aa2af9bb8`) and the v0.9 development runtime.
