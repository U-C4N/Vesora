# v0.9.0 measured evidence

## Scientific 3D matrix

The measured build reuses geometry and GPU buffers during camera-only frames. Cached picking is much cheaper than its first index build. These results do **not** establish 60 FPS or interactive 500,000-point performance: the software renderer takes hundreds of milliseconds for the largest orbit frames, and the first 500,000-point pick is a visible pause.

Run the matrix without another browser, Qt, or graphics benchmark running:

```sh
npm run build
node scripts/benchmark-3d-v09.mjs
```

The script writes raw timing samples, diagnostics and provenance to `artifacts/v09/3d-software.json`. Set `VESORA_SOFTWARE_GPU=0` to measure the browser's default backend separately; its actual renderer is recorded. This measurement used only the software backend.

### Recorded environment and scope

- Recorded: 2026-10-15 08:42:35 UTC; Windows; Intel Core i9-14900HX; 32 logical CPUs; 34,045,042,688 bytes physical memory.
- Chrome 155.0.8059.41, ANGLE Vulkan 1.3.0, SwiftShader Device (Subzero), SwiftShader driver.
- Runtime: `packages/core/dist/index.js`, SHA-256 `b1083ef255ac4f27e93b8e6919b957c4d011b6e43c1d324f7f056e5f38984ca1`. These measurements identify this build, not a different later release artifact.
- Canvas: 1000 × 600, DPR 1. Three repeats per case, alternating case order. One unmeasured small surface and scatter scene precede the matrix; every measured case uses a fresh page.
- Surfaces use the same finite synthetic radial field, smooth shading, no wireframe. Scatter uses seeded uniform spatial coordinates, seed 42, point size 3. No adaptive geometry detail is enabled.
- First-ready time includes figure creation, source registration, mounting and `ready()`, then `gl.finish()`. Data generation is excluded and recorded separately. Each orbit sample includes `ready()` and `gl.finish()`; 30 samples per repeat.
- Cold picking includes the projected index build. Each repeat then records 100 synchronous hover samples at different positions with an unchanged camera. Warm picking includes the committed hover/tooltip path of a bare figure, not a shared viewer sidebar and not only its numeric search.

### Timings

All values are milliseconds. First-ready and cold-pick columns are medians of three runs. The p95 columns are the median of the three per-run nearest-rank p95 values, not a pooled p95.

| Scene | First ready, GPU complete | Orbit p95 | Cold pick | Warm pick p95 |
| --- | ---: | ---: | ---: | ---: |
| Surface 128 × 128 | 124.6 | 35.1 | 13.6 | 1.1 |
| Surface 256 × 256 | 196.3 | 62.7 | 21.9 | 2.1 |
| Surface 512 × 512 | 236.0 | 146.7 | 72.0 | 5.1 |
| Scatter 10,000 | 103.3 | 14.7 | 12.8 | 0.2 |
| Scatter 100,000 | 117.9 | 46.4 | 17.2 | 0.4 |
| Scatter 500,000 | 274.6 | 250.5 | 228.6 | 3.2 |

Variability matters: the 500,000-point cold pick ranged from 221.4 to 242.1 ms, orbit p95 from 171.4 to 263.1 ms, and warm-pick p95 from 2.9 to 7.8 ms. A camera change invalidates the projected index; the next pick is cold again. An object-space index or asynchronous index construction remains a potential follow-up, not a shipped performance guarantee.

All 18 runs passed the script's assertions: exact canvas dimensions, no WebGL error, no geometry rebuild or GPU upload during the 30 camera-only frames, no index rebuild during the 100 warm picks, and zero source bytes after close. Candidate p95 was 7,615 of 500,000 points and 9,226 of 522,242 surface triangles in the largest cases; overlapping projections still require exact depth tests.

The reproducible evidence is [the benchmark script](../../scripts/benchmark-3d-v09.mjs) and its raw JSON output. The practical finding is that camera changes reuse GPU data and repeated hover avoids a full scan. The next performance work should address cold-index latency and large-scene draw cost; no speedup against v0.8, hardware-GPU result, automatic LOD, or live-3D throughput is inferred from this matrix.

## Paired v0.8 regression check

Five paired repeats used the archived v0.8 core tarball (SHA-256 `ab36142c084f0b33236e47d248c5ff9ab81bf4b4ef0e0c2bd4f7216aa2af9bb8`) and the v0.9 development runtime. Both ran on the same Windows/Chrome SwiftShader host, 1000 × 600 canvas, DPR 1, seed 42, one million samples and 100 viewport interactions per run. The order alternated each repeat. Raw samples are in `artifacts/v09/regression-software.json`; rerun with `node scripts/benchmark-v09.mjs regression`.

| Workload / metric | v0.8 median (ms) | v0.9 median (ms) | Change | ≤10% regression gate |
| --- | ---: | ---: | ---: | --- |
| Density first ready | 182.6 | 177.5 | −2.79% | Passed |
| Density interaction p95 | 241.6 | 236.6 | −2.07% | Passed |
| Line first ready | 185.4 | 184.0 | −0.76% | Passed |
| Line interaction p95 | 172.7 | 186.5 | +7.99% | Passed |

Each p95 is computed within one run before taking the median of five p95 values. Individual runs varied substantially; the line has a modest measured regression and is not described as a speedup. These viewport interactions are not the streaming append latency workload and do not establish its ≤150 ms gate.

Measured v0.9 runtime SHA-256: `5a477ca63ee85be6d7e8bca82f8b18819e228ff1106f4218447c05ab5c80b62a`. Baseline runtime SHA-256: `4152b55834a349a6d81e1394617d17c0463e801b8e21e97ca6f78d8049712bfc`. Later release builds need their own hash-linked evidence. The 30-minute p95 ≤50 ms / p99 ≤100 ms and ≥80% worker-transfer reduction remain optimization targets until measured on that exact reference workload.
