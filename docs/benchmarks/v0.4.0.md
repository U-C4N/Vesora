# Vesora v0.4 statistics benchmark

This is one observed **SwiftShader software-rendering** run, not a hardware-GPU result, speed guarantee, FPS measurement or comparison with another library.

## Reproduce the measurement

Run from the repository root in PowerShell:

```powershell
npm run build
$env:VESORA_SOFTWARE_GPU = '1'
npm run benchmark:statistics
```

The [benchmark script](../../scripts/benchmark-statistics.mjs) writes every latency sample, scheduler cache observation, representation and environment field to `artifacts/benchmark-statistics.json`. `VESORA_CHROME` can select another Chromium executable; record those results separately. Leave `VESORA_SOFTWARE_GPU` unset for a separate hardware-rendering experiment and inspect the reported renderer rather than assuming GPU acceleration.

## Environment and method

- Recorded: 2026-10-10, 14:22:27 UTC / 17:22:27 Europe/Istanbul.
- CPU: Intel(R) Core(TM) i9-14900HX; 32 logical CPUs; 31.7 GiB system memory.
- Platform: win32 / x64; headless Chrome 155.0.8059.39.
- Reported renderer: `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)`.
- Figure: 1,000 × 800 CSS pixels at device pixel ratio 1, inside a 1,200 × 1,000 browser viewport.
- Each of the four cases opens a **fresh page in the same browser**. Case order is 100k histogram, 100k boxplot, 1m histogram, 1m boxplot. No warm-up case or latency sample is discarded. Browser process, shader compilation, CPU scheduling and background system load are not reset or controlled between pages.
- Initial data uses an LCG with seed 42 and Box–Muller normal samples. Every 997th sample receives a `+10` tail offset. The replacement dataset uses seed 4242. Histogram uses 100 bins with probability-density normalization; boxplot divides the total sample count into eight equal groups, shifts group `i` by `0.125 × i`, and shows all fliers with `whis=1.5`.
- Input and replacement-array generation are measured separately and **excluded** from first-ready and update-ready latency.
- **First preparation** measures the first `queryStatistics()` promise, including source registration/copies, worker loading and exact summary work. **First ready** starts before figure creation and ends at `ready()`, so it additionally includes API validation, mount, scheduling and drawing. The difference is not a standalone GPU-render-time measurement.
- **Update ready** measures `layer.setData(...)` through `ready()` after replacing every raw sample buffer. Each pan phase contains 20 programmatic view changes through `ready()`, before and after the update. These are latency samples, not an animation frame-rate test.
- Median averages the middle two samples. The p95 uses nearest rank: the 19th value among 20 sorted samples.
- Cache hits are observed by returned summary-object identity, with cache bytes/entries before and after every request. They are not inferred from short latency.
- JS heap is Chromium's **main-page** `usedJSHeapSize` estimate at the end of each case, without forced garbage collection. It is not a peak, process-total or reliable worker-memory measurement. Python and GPU allocation sizes are unmeasured and stored as `null`.

All four cases completed with WebGL error code 0. Each source replacement was a summary-cache miss; every pan reused its current-source summary. Final accounted summary-cache sizes were 32,512 bytes for either histogram, 105,344 bytes for the 100k boxplot and 1,024,640 bytes for the 1m boxplot. These are the scheduler's conservative object-size estimates, not measured allocations.

**What this establishes:** these seeded cases counted and summarized the complete input, recomputed summaries after raw-source updates, and reused them during pan. It does not establish universal latency, linear scaling, a hardware frame rate, or a speed advantage over another library. A larger case appearing faster in a pan column is not evidence of a size-related speedup.

## Statistical contract and limits

The accompanying [unit tests](../../tests/unit/statistics.test.ts) check bin-edge inclusion, unequal-width density normalization, cumulative probability, constant/empty data, non-finite omission, exact quartiles, source-index preservation, dependency-version capture, cancellation and bounded caching. They are separate correctness evidence; this timing run is not a substitute for them.

- Histogram bins are left-closed/right-open except the last, which includes its right edge. Density uses included samples and bin width; cumulative density is a probability CDF. `valid` counts finite source values; `rangeExcluded` counts finite values outside the selected edges.
- Boxplot quartiles use `h=(n−1)p` linear interpolation. Default whiskers use actual observations within the 1.5-IQR fences. **Empty-fence fallback is explicit:** if no observation lies between an interpolated quartile and its fence, the corresponding whisker ends at Q1/Q3. For `[0, 1]` with `whis=0`, whiskers are `0.25` and `0.75`; both observations are fliers. This avoids reversed whiskers without inventing source observations.
- Input arrays remain unchanged. Sorting uses bounded chunks and cooperative merge passes; histogram scans, large edge lists and final mark-bound scans also yield for cancellation. This does not promise a hard real-time cancellation deadline.
- Pan-time inspector counts refer to samples belonging to **intersecting whole bins or groups**, not an exact raw-sample viewport filter. The raw-data summary remains exact; rendered counts identify bins/groups with visible marks.
- The default summary cache is bounded to 32 MiB of accounted results. A summary larger than the cache budget is not cached. Exact geometry has a 2,000,000-vertex limit after viewport clipping and fails explicitly instead of silently sampling fliers or bins.

For the feature API and update contracts, see [API and usage](../api.md).
