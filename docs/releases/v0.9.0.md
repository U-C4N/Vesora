# Vesora v0.9.0 — PRISM release checklist

**Status: `0.9.0-rc.6` is in development. Its release gates remain pending until reviewed evidence is bound to its final archives. No npm, PyPI or GitHub publication is claimed.** PRISM connects scientific 3D inspection and bounded telemetry through an optional Obsidian viewer.

RC5 passed core/React/Python correctness, installed-package and browser checks. Its performance gate failed: the one-million-point line first-ready median was 180.9 ms against the fixed v0.8 baseline of 163.2 ms (+10.8456%, limit 10%). Its real Jupyter recovery probe also exposed a stale kernel subshell route that could prevent acknowledgements after reconnect. **RC6 contains a numerically equivalent source-summary optimization and a per-widget compatibility guard for deleted cached subshell routes. Its final archives require fresh validation.** The original failed results remain recorded. See the [measured evidence](../benchmarks/v0.9.0.md) and [historical evidence appendix](v0.9.0-history.md). No earlier result establishes a later candidate's gate status.

## Validate the agreed scope

| Area | Behavior to validate |
| --- | --- |
| Scientific scenes | Mixed 2D/3D grids, 3D lines, camera presets, equal axes/fit/selection focus, surface presentation, source-aware picking and exact surface row/column slices |
| Telemetry | Explicit accepted/rendered append waits, bounded live windows and independently frozen inspection snapshots |
| Identity | Displayed frame/source revisions and stream epochs/sequences; React row references retained for live, rendering and frozen windows |
| Viewer | Shared scoped dark/light chrome, borrowed figure ownership, inspector, diagnostics, camera/slice controls and displayed exports |
| Python hosts | Negotiated transport v3 with separate data acknowledgement/frame reporting and frozen-view event validation |
| Distribution | Canonical release identity, exact archive hashes and publication of verified files |

Use the [PRISM API and migration guide](../prism.md) and React example at `?demo=workbench`. Existing SaaS and producer-pause telemetry examples remain available. Scene protocols 1–6 remain readable; protocol 7 carries the new scientific scene contracts. Python facade exports retain accepted-state semantics; the connected viewer exports its displayed frame. Renderer-local inspection controls do not imply full Python/JavaScript API equivalence, and bounded snapshots do not replace application-owned complete history.

Bounded 3D trajectories, rolling surfaces, A/B pins and manual sampling remain explicit `@vesora/core/labs` experiments, isolated from default imports. Every shipped experiment must pass data integrity, isolation, cleanup, export and applicable performance checks. **Automatic adaptive 3D level of detail is excluded from the stable release; the Labs manual sampling helper does not implement it.** General mesh/volume rendering, arbitrary clipping planes and unrestricted 3D streaming also remain outside stable scope.

The release-blocking platform is WebGL2-capable desktop Chromium on Windows 11, Windows QtWebEngine, and JupyterLab 4 with the tested widget/kernel stack. Python contracts cover 3.10, 3.11 and 3.14. Record exact browser, Python, Qt, widget, React, OS and GPU versions for each run. Python's existing PySide6/aiohttp base dependencies and optional NumPy/notebook dependencies are unchanged.

Firefox and Playwright WebKit are compatibility-smoke targets; WebKit automation does not establish Safari/iOS support. macOS/Linux desktop graphics and mobile Safari remain unclaimed until executed host/device evidence exists. WebGL2 is required. The historical v0.8 30-minute browser soak and shortened v0.9 diagnostics do not satisfy the two-hour gates.

## Build and verify the fixed candidate

1. Complete source checks and freeze the feature list. Use npm `0.9.0-rc.6`, Python `0.9.0rc6` and Git tag `v0.9.0-rc.6`. Commit all intended changes, confirm a clean tree and place the matching tag on that commit.
2. Build once from that clean tagged commit, then package without `--candidate`:

   ```powershell
   npm run build
   npm run package:release
   npm run init:release-gates -- dist/release-v0.9.0-rc.6
   ```

   The Python build environment needs `setuptools>=77` and `wheel`. Packaging writes three archives, ten demos, `release-manifest.json` and `SHA256SUMS.txt`. The manifest binds commit, tag, source-tree state and index/worker/viewer/Labs hashes. `--candidate` is only for local review archives; the publisher rejects those files even if the source commit was clean and tagged.
3. Verify the exact file set, checksums, archive runtime and all ten offline demos with `npm run test:release -- dist/release-v0.9.0-rc.6`. Run `npm run test:packages` for installed packages and the default React 19 consumers, then run `npm run test:consumers -- dist/release-v0.9.0-rc.6` with `VESORA_REACT_VERSION=18.3.1`. Installed consumers derive their expected Vesora version from the archive manifest. Complete the remaining suites, real-host runs, benchmarks and human checks against the same bytes; run graphics measurements sequentially.
4. Preserve raw evidence inside the release directory and add reviewed JSON reports. Each report identifies its `gate`, `status`, `version`, `commit` and `manifestSha256`, plus results, environment and raw evidence references. Its path and SHA-256 go in that gate's `evidence` array in `release-gates.json`. Initialization creates only pending gates and does not overwrite an existing file. Mark only completed, reviewed gates passed.

Rebuilding packages changes their evidence identity; retain previous records and validate the new files. An RC-to-final version change also requires a new build and verification. See the [development guide](../development.md#validate-a-release-package) for tooling and the [measurement procedure](../development.md#measure-prism-performance) for unchanged reference workloads.

## Run the human checks

Use the [Turkish pilot packet](../pilot/v0.9.0/README.md) with three researchers/analysts and two telemetry developers. Start the fixed archive with `node scripts/run-pilot-v09.mjs dist/release-v0.9.0-rc.6`; give participants only its task sheet. The observer records candidate hashes, environment, timing, assistance, errors and exported files in the generated form.

The approved criterion remains **at least four of five participants completing surface → slice → freeze → export without assistance**. Every produced offline snapshot must reopen with matching selected sample identity and values. Preparing participants, a synthetic fixture or an empty form is not a successful session. Own-data onboarding time, extra keyboard tasks, preferences and repeat use after two weeks are optional research, not additional pilot gates.

Run the separate [Narrator/NVDA checklist](../qa/v0.9.0-screen-reader.tr.md) for the existing accessibility gate. Automated [viewer QA](../qa/v0.9.0-viewer.md) does not replace actual screen-reader operation. Missing human results remain pending.

## Publish only verified archives

Publication is separate from builds and tests. The publisher requires all ten machine-readable gates, matching local and origin tags, and verified artifacts/checksums. npm candidates use `next`; final `0.9.0` uses `latest`. Python prereleases keep their explicit PEP 440 version.

GitHub uploads go to a draft first. An interrupted upload can resume by downloading and hashing existing assets, then adding only missing files; different bytes are rejected without replacement. Never overwrite a published version. After each channel upload, download the exact npm/PyPI/GitHub version, compare hashes and execute clean consumer smoke checks. Upload success alone is not verified publication; failed re-verification clears the publication-complete flag.

The [release guard tests](../../tests/scripts/release-validation.test.mjs) and [GitHub upload tests](../../tests/scripts/github-release.test.mjs), run by `npm run test:release-contracts`, exercise these contracts without publishing or making network requests.

The [v1 readiness list](v1-readiness.md) records remaining acceptance work, measured limitations and later product decisions without changing this release's gates.
