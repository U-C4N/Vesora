# Vesora v0.9.0 — PRISM release checklist

PRISM connects scientific 3D inspection and bounded telemetry through an optional Obsidian viewer. **This document describes an in-progress release candidate, not a published npm, PyPI or GitHub release.** Registry credentials, a clean tagged build, executed release gates and downloaded-artifact verification are still required before declaring publication complete.

Read [the PRISM workflow](../prism.md) for the implemented APIs and examples. Existing scene protocols 1–6 remain readable; protocol 7 carries the new scientific scene contracts. Streaming/inspection runtime state is not a replacement for application-owned complete history.

## Platform contract

The initial release-blocking target is a WebGL2-capable desktop Chromium environment on Windows 11, Windows QtWebEngine, and JupyterLab 4 with the tested widget/kernel stack. Python contracts cover 3.10, 3.11 and 3.14; React consumers cover 18.3 and 19. Record exact framework, browser, Python, Qt, widget, OS and GPU versions in each final run.

Firefox and Playwright WebKit are compatibility-smoke targets. A Playwright WebKit run does not establish actual Safari/iOS support. macOS/Linux desktop graphics support and mobile Safari remain unclaimed until executed host/device evidence is recorded. Core rendering still requires WebGL2. Python's existing PySide6/aiohttp base dependencies and optional NumPy/notebook dependencies are unchanged by this UI work.

## Candidate and public release flow

1. Freeze the candidate feature list. Any shipped Labs experiment must pass data integrity, cleanup and export correctness; defer experiments that fail their isolation or performance checks.
2. Use one canonical release identity with ecosystem spelling: npm `0.9.0-rc.1`, Python `0.9.0rc1`, Git tag `v0.9.0-rc.1`. Subsequent candidates increment the candidate number.
3. Build once from the clean tagged commit. Package the core/React tarballs, Python wheel, offline demonstrations, manifest and SHA-256 file. Record source commit and runtime/worker/viewer hashes.
4. Run installed-consumer and real-host gates against those exact files. Store evidence paths and hashes; do not mark an unexecuted gate passed.
5. Publish the verified archives to GitHub, npm and PyPI. The npm candidate channel is `next`; final `0.9.0` uses `latest`. The Python prerelease is explicitly versioned. An RC-to-final version change requires a new final build and verification.
6. Download each exact version from its public endpoint, compare hashes and run clean install/import/export smoke checks. An upload success alone does not establish verified publication.
7. If a channel fails, retain the successful upload identities and retry only the missing channel. Never overwrite a published version; repair with a new candidate/patch release when bytes must change.

The release evidence file must refer to the manifest's SHA-256 and include the final commit. `scripts/publish-release.mjs` requires passed correctness, browser, Qt, Jupyter, React-consumer, package, soak, accessibility and beta-pilot gates. GitHub publishing also requires an existing matching tag. Publishing is not part of ordinary builds or tests.

`npm run init:release-gates -- dist/release-v0.9.0-rc.1` creates a pending `release-gates.json` without overwriting an existing file. Each gate needs a reviewed JSON report under that release directory, referenced as `{"path":"evidence/soak.json","sha256":"<report SHA-256>"}` in its `evidence` array. A report contains `gate`, `status`, `version`, `commit`, and `manifestSha256`, plus the gate's actual results, environment and raw evidence references. Its identity fields must match the release manifest. Human accessibility and pilot reports use the same binding; this schema does not turn missing human work into a pass. Retain and review the underlying evidence before setting a status to `passed`.

Publication rejects local `--candidate` archives even when their commit is clean and tagged. It checks every expected artifact, the checksum file and the local and origin tags' resolved commits before starting an uploader. Installed consumers derive their expected Vesora version from the supplied archive manifest. Public verification downloads the manifest and checksum file as well as all package/demo assets; any failed re-verification clears the publication-complete flag. The pure Node guard regression suite is `npm run test:release-contracts` and makes no publication or network requests.

GitHub assets are uploaded to a draft before it is published. Retrying an interrupted upload downloads and hashes every already-present asset, then adds only missing files. Different bytes are rejected without replacement; an incomplete immutable release requires a new release identity.

## Pilot acceptance

Recruit three researchers/analysts and two developers who operate telemetry. The approved publication gate is **at least four of five participants completing the surface → slice → freeze → export workflow without assistance**. Every produced offline snapshot must reopen with matching selected sample identity/values. Use the [Turkish pilot packet](../pilot/v0.9.0/README.md) and record candidate hashes, environment, task, timing, assistance, errors and exported files.

Own-data onboarding time, additional keyboard tasks, qualitative preferences and repeat use after two weeks can be studied separately. They are optional research, not extra release gates. No participant has been counted as successful by preparing the packet. A failed required workflow should lead to a concrete fix or scope change before declaring the gate passed.
